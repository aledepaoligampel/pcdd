# PCDD — Progressive Change-Driven Development

Each change, just enough process. Project-specific instructions override these defaults within the agent's constraints. This does not authorize external effects or expand the user's request.

The kit's instructions and source templates are maintained in English. Respond in the user's language and write project documents in the project's agreed language, falling back to the user's language if none is established. Preserve original quotations and approvals verbatim. Keep command names, identifiers, and machine-parsed syntax unchanged; the CLI language setting controls terminal output only.

1. Understand the request and discover context before asking the user for paths: inspect relevant files and locate project instructions, overview, planning, continuation notes, and manifests where available. Read only what the request needs. Do not require a particular context filename or load the entire history. If several active efforts fit the request, ask which one to continue. Questions and research do not authorize implementation. Well-understood, bounded work that can be resumed from the diff proceeds directly, without a separate change document or routine delegation. Assess risk independently of size.
2. For substantial work, read the `pcdd-work` skill installed for your agent. Use a document at `pcdd/changes/<name>.md`. Do not load all changes or their history at startup; resume from the continuation section and relevant specs/tasks. For requests to save progress or continue where work stopped, consult `pcdd-work` to preserve or recover the continuation point without loading the entire history. Recognize these requests in the user's language and preserve existing section names, including `Continuación` in older documents.
3. Before implementing a change, present verifiable specs with the user's quotations and wait for approval. Record the actual approval. Do not request approval again when already granted. An extension requires approval only for the new scope.
4. Use test-first development when a deterministic test and clear expected result exist: observe RED, GREEN, then refactor. Verify behavior through public interfaces. Otherwise explain the alternative evidence and what remains unverified.
5. Identify risk: (1) persisted data or irreversible effects; (2) security; (3) external contracts; (4) concurrency; (5) delivery/environment; (6) lack of coverage; (7) money/tax. Use `Risk: none` or `Risk: item N (reason)`. Prefer a coherent unit over an artificial 400-line split.
6. Before committing, run the gate configured in `.pcdd/config.json` and the database gate if applicable. If empty, investigate existing scripts and tools and configure real commands during authorized work, preserving the project's settings. If no application exists yet, define gates with its first scaffold and tests; do not use benchmarks as the product gate or invent commands. Ask only when a real decision is unresolved. Empty does not mean passed. High risk also requires `pcdd-review`, code review and independent verification after the gate, and human approval based on an understandable summary. For small risky work, create a minimal record of criteria, evidence, and approval.
7. For work tracked in a change, check the current session's exposed tools for native task tracking. When available, use them to mirror the change's tasks at startup/resumption and after state changes; preserve PCDD task IDs in labels and derive all states from the document. Update the document first; the native view is not a second plan. If the tools are absent or cannot represent the state, explain the limitation at startup or when encountered; do not claim text lists are native tasks. Also show a brief chat block when starting or resuming and when task status changes: completed count, relevant completed tasks, active task, and next step or blocker. During long operations, explain what is still running and what remains unknown without inventing progress. Use the CLI (`pcdd status <name>`) for task counts. Do not invent savings or ETAs.
8. The user tests the result before the change is declared done. Completed tasks do not imply acceptance. Push, PR, merge, and publication require explicit instructions; commits follow the project's authorization rules.

For Git commits, use `pcdd-commit`; to organize pending changes into coherent commits, use `pcdd-commit-review`. These skills do not replace the high-risk review checkpoint. Review-only requests do not authorize index or history changes. Whether or not a commit skill is loaded, preserve the user's Git identity and never add `Co-Authored-By` trailers, textual signatures, or AI attribution to commits or PR descriptions. Respect the project's cryptographic signing configuration and hooks; cryptographic signatures are not AI attribution.

Configuration belongs to the project. Do not customize managed core or skill files; use `AGENTS.md` and `.pcdd/config.json`. PCDD requires no external memory, MCP, or particular editor.
